# 阶段提示词：检查点续接与最小 Pi 控件

继续当前 `pi-continuity`，阅读规格与实际代码。本阶段实现能够被人检查的续接与恢复，不增加宏大记忆平台。

## 一、恢复协议

提供三种明确操作：
- inspect：只读查看旧检查点，当前运行和工作区都不变。
- correct：在当前状态生成一次纠正修订，旧证据和旧版本不被原地改写。
- fork/resume：从已发布检查点创建新分支和新 epoch，重建活动会话。

不提供语义模糊的“一键全部回滚”。首版没有可靠代码恢复，就只提供“上下文续接 + 工作区一致性检查”，并在 UI 明确说明。

续接流程必须协调旧运行的停止、待保存结果、用户队列、工作区描述、可见证据范围和 SDK 资源重建。每一步失败都返回可观察状态，不把部分完成标成成功。

认知快照之外保留当前权限、敏感删除约束、单调 epoch 和操作审计。外部操作处于 unknown 时不自动重试；恢复不是历史工具重放。

strict 模式只允许检查点当时可见内容。practical 模式可由用户明确选择导入旧尝试的失败记录；保留来源和适用条件，不能伪装成当前代码事实。

工作区与检查点不匹配时进入待核实/受限状态。不能仅用 Git HEAD 断言所有文件一致，也不能自动 reset/clean 用户工作。

## 二、最小 UI

先查当前 Pi 支持的 TUI / extension 组件，不凭旧 API 编写。

实现一个入口（例如 `/continuity`，实际命名可调整）和少量子操作：
1. 状态面板：模式、task、epoch、当前 contract revision、已发布检查点、未归档/未整理状态、最近真实故障。
2. 当前任务与请求视图：能查看原话来源、有效限制、提案、实际本轮包含的材料；UI-only 卡片不增加模型上下文。
3. 检查点详情与差异：显示记忆、会话及工作区覆盖范围；恢复确认明确显示是 strict 还是显式导入经验。

点击操作调用宿主的版本校验和恢复协调器。不要把按钮实现为“向模型发一句请帮我恢复”。用户确认身份由宿主处理，不能允许模型自行调用工具伪造批准。

不做独立 Web 应用，不做复杂拖拽时间线，不做通用文件编辑器。先确保三个视图能说明系统实际状态。

## 三、验收

- inspect 前后 active ref、epoch、工作区不变。
- correct 产生新修订，旧快照读取结果不变。
- fork/resume 使用新 epoch，旧任务的晚到写入被拒绝。
- strict 模式的搜索、直接 ID 读取和缓存均不能返回后续记录。
- 显式导入失败经验有来源、选择记录和版本；不能默认自动导入。
- 在任一恢复准备步骤注入失败，未完成检查点不被激活。
- 重建后只存在正确的 SDK 订阅，不重复消费事件或用户输入。
- UI 关闭或重绘不会执行业务修改；确认后也要重新检查 expected revision。
- 界面如无法自动化渲染测试，提供 reducer/action 集成测试及可执行手工清单，明确未测试部分。

更新 README 与 VALIDATION，提供隔离测试任务和几条实际可运行的演示命令。不要把状态面板截图当作恢复机制正确的证据。
