# 评测提示词：证明收益，而不是证明设计很复杂

评测当前 `pi-continuity`。先检查核心正确性缺陷是否修复。严重的续接、隔离或重复副作用问题尚未解决时，不开展“效果提升”宣传。

## 对照组

A：固定版本的 Pi 原生上下文行为。
B：任务约定、自动事件/证据记录、旧工具输出移出与最小接续包，不启用额外经验整理。
C：在 B 上增加已有的可选经验便条/局部摘要/检索增强。

C 尚未实现时跳过，不为了凑评测先造功能。记录准确配置，不把改了模型、预算和工具集的结果混为同一实验。

## 任务集合

至少设计小型、可复现的本地仓库任务，覆盖：
- 多阶段功能修改，中途只有“继续”，必须遵守早期兼容性限制；
- 用户改变约束，旧方案应失效但原始证据保留；
- 长调试里有一条失败尝试，后续返工不能无依据重复；
- 笔记与实际工作区冲突，需要主动检查；
- 至少两次上下文切换及一次进程重启；
- strict 历史分支与显式导入失败经验；
- 一条未被便条记录的关键细节需要从原始证据取回。

不要只做 needle/暗号复述测试。验收应包含代码测试、约束检查和副作用记录。

## 指标

记录任务验收结果、关键约束违反、错误决定写入、重复失败、无效/错分支检索、未知操作处理，以及总输入输出 token、额外整理/检索调用数、耗时。

明确哪些指标程序判定、哪些人工核查。额外模型调用和失败重试计入总成本。mock 无真实 token/费用时标为不适用，不编造账单或假精度。

## 诊断与消融

对相同任务分别提供：
1. 实际自动检索的接续包；
2. 测试人员准备的已知相关证据包。

两者差异帮助区分检索/组装问题与模型执行问题。再比较自动便条和人工校对便条，定位写入错误。

B 与 C 相当时优先 B。原生 Pi 更好时如实报告，分析退化条件，而不是调换口径。

## 执行要求

先运行不需要账号的结构与故障测试。真实模型测试仅使用明确配置、获准的提供方和预算；缺凭据时交付完整可运行脚本与小数据集，报告“真实质量尚未评测”。不要把 mock 成功等同真实模型提升。

真实结果保存原始运行记录、配置、模型标识、上游版本和统计脚本。小样本只报告观察，不宣布普遍优越；有多次运行时展示离散程度而不只报最好一次。

最终报告：在哪些任务上更好/相当/更差，代价是什么，哪些模块值得保留，哪些应删掉，下一轮最小修改是什么。
