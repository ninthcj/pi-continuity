# 总任务提示词：实现基于 Pi 的任务续接引擎

你是这个项目的实现工程师。请在当前工作区实现一个基于原版 Pi 的任务续接引擎，暂称 `pi-continuity`。这是实际编码任务，不是只写架构说明。

## 一、目标与取舍

目标是让长时间 coding task 在多次上下文切换、进程重启和有限返工后，仍保留正确的任务要求、可核实的进展及证据入口。

采用：
**最小任务约定 + 自动工作记录 + 原始证据档案 + 有界近期上下文 + 按需续接 + 少量可选经验便条。**

不要把整个项目复制成一份由模型维护的百科。代码结构和当前配置优先从工作区读取或使用带版本的缓存；重点保存不能廉价重建的用户约束、决策原因、失败条件、未完成状态和证据。

允许局部摘要和交接说明，但它们不是唯一事实来源；不要把“上一份摘要再总结一遍”作为唯一续接机制。也不要把“完全不用摘要”当作产品 KPI。

COW、Btrfs、ZFS、reflink、向量搜索、知识图谱、多 Agent 自动合并均不属于首版目标。先证明任务续接有效，再决定是否增加这些能力。

## 二、开始前必须完成的核查

1. 读取仓库现有的开发约定、AGENTS.md、README、依赖锁文件和测试命令。保留现有工作，不能覆盖不属于你的修改。
2. 核对当前实际使用的原版 Pi 包、官方上游、版本或提交；不要默认 Oh My Pi，也不要照搬旧聊天里的包名、事件名、API 参数。
3. 查实际源码和测试，确认：消息构造顺序、模型请求最终发送点、工具执行顺序、事件是否被 await、异常是否被吞掉、自动重试、自动压缩、用户输入队列、会话替换与取消语义。
4. 尤其检查：扩展处理器抛错后是否仍继续发请求。不能把“回调里 throw”当作天然可靠的阻断机制。
5. SDK 能做到的优先使用 SDK。必要时允许一个小而明确、可测试的核心补丁；不要在大量扩展钩子之间绕行来伪装正确性。
6. 先记录已验证的接口及源码位置，再实现。若联网或依赖获取不可用，完成独立核心和真实契约的 mock 边界，明确标注未验证的 Pi 接入；禁止编造 SDK。只有任务确实因此无法继续的部分才算阻塞。

不要修改用户全局 Pi 配置、读取无关凭据、切换磁盘格式、部署服务或对现有项目执行破坏性 Git 操作。以隔离测试目录和当前项目配置为主。空仓库可自行建立最小项目结构；技术栈优先沿用现有项目，独立新项目优先 TypeScript。

## 三、职责划分

### Pi 执行层

继续复用 Pi 的模型接入、编码工具、消息协议和交互能力，不从零写 coding agent。

### 受控宿主 / Pi adapter

拥有模型请求放行、工具执行放行、事件持久化、安全停止、上下文组装、会话重建及运行代际隔离的关键路径。

### 独立 continuity core

负责任务约定版本、证据引用、工作记录、检查点、作用域读取与接续包。不得依赖 TUI，也不要依赖未经隔离的 Pi 内部会话文件格式。

### Pi 扩展界面

显示状态、任务约定、实际请求视图、检查点与差异，并触发宿主命令。界面不得靠向模型发送“请恢复”来冒充真正的恢复操作。

模块边界保持清楚，但不要为了形式拆成十几个包或微服务。

## 四、数据模型：少量权威对象，不建立第二个项目真相库

下面列的是语义要求，表名和类型名可按现有仓库调整。

### 1. TaskContract：当前任务约定

包含稳定任务 ID、修订号、目标、验收条件、有效限制、用户原话证据引用、已撤销或被替代的要求。

- “继续”“按前面做”应延续原任务及有效要求，不能只保留最后一条消息。
- 模型解释是 proposed；重要决定、权限与约束的 confirmed/retired 状态由明确用户事件或宿主规则产生，不能由模型自报获得。
- 不强行把所有自然语言解析成布尔规则。无法确认的要求保留原文与歧义。
- 最新明确的关键约束变化必须让旧请求视图失效；不能为保持缓存命中而继续执行旧要求。

### 2. EvidenceEvent：证据与事件

由宿主记录项目、任务、分支、事件 ID、单调序号、运行代际、操作 ID、来源类型、时间、负载或 blob 引用。

- 区分用户输入、模型解释、工具调用、工具结果、人工确认、文件观察。
- 尽量保留实际可获得且允许保存的消息结构、附件引用和完整工具结果。截短的展示不等于完整证据。
- 标明 captured / incomplete / redacted / unavailable 等可用性，不承诺恢复从未收到或未获准保存的内容。
- 不记录 API key、OAuth header 等凭据；不尝试获取模型隐藏推理。对接口返回的 opaque/signed 内容按提供方规则处理，不伪造或重新签名。
- “已存档”“已索引”“已整理”“已确认”必须分开。处理序号只表示流程覆盖，不证明语义理解完整。

### 3. WorkRecord：工作记录

记录文件变更、工具执行、测试命令、返回结果、观察到的工作区版本和未完成操作。能由工具自动记录的，不让模型重复口述成为唯一来源。

- 严格区分决定、观察、推断、任务状态、验证结果。
- 工具成功不等于业务验收完成，部分测试通过不等于全部功能正确。
- 观察需带适用条件。代码版本不能只写 Git HEAD 却忽略 dirty/untracked 变化；使用明确覆盖范围的文件清单或指纹，无法覆盖的标为未知。
- 不要求每轮全量扫描仓库；只对需要依赖的验证范围建立可解释的匹配规则。

### 4. OptionalNote：经验便条

只保存高价值原因、失败经验与昂贵调查结论，带适用范围、版本和证据。可选层，不得成为续接唯一依赖。

更新保留旧版本；共享的旧版本不能被原地标记过期。适用性由“所选版本 + 依赖版本 + 当前环境”判定。

### 5. RequestManifest：本轮实际请求视图

记录所用 contract revision、memory/checkpoint ID、run epoch、包含的事件/便条/证据、必要排除原因或范围、工具与模板版本、输入预算及估计误差。

目标是能回答“这轮模型究竟看见了什么”，不只是显示一个记忆总数。引用的请求输入应可追溯；不要额外泄露敏感信息。

### 6. Checkpoint 与 OperationLedger

Checkpoint 关联任务、记忆修订、可见历史位置、工作区描述、格式版本和未完成操作状态。

只有准备完整的检查点才发布。区分“记忆已保存”与“工作现场可续接”。

OperationLedger、运行代际、当前权限和删除约束独立于可回滚认知状态。外部操作结果未知时保存 unknown；不得假装 exactly-once，也不得因恢复而盲目重试。

## 五、存储与提交

首版使用适合当前运行时的 SQLite 驱动；大附件和长结果存在普通文件中；代码版本优先利用 Git。驱动选择必须实际验证，不强行升级整套运行时。

SQLite 是小型权威元数据与修订记录存储。Markdown 是导出/审查视图；人工编辑需明确导入，不能两边静默覆盖。检索索引可重建，不是第二份权威历史。

每次语义修改带 expected revision、run epoch 和唯一 op_id。过期修改拒绝，不用 last-writer-wins。

模型分析在数据库事务外完成。新修订、相关状态和当前指针在短事务内提交。blob 先完成可靠保存与校验，再提交引用；失败只允许产生可清理的未引用对象，不发布悬空引用。

提交结果未知时按 op_id 查询，不盲目重复写。数据库原子性不扩展到 Git、附件目录或外部 API。

使用 schema version 和可测试迁移。解释不了旧关键字段就拒绝恢复，不猜默认值。备份不能只复制运行中的 SQLite 主文件而漏掉它所依赖的数据；按实际驱动和 SQLite 支持方式实现或明确要求停机备份。

## 六、写入与安全边界

- 单主 Agent、单受控写入者起步；可能产生变更的工具默认串行。无法可靠判断的 shell 操作按保守策略处理。
- 有副作用的工具执行前保存操作意图；结果保存后才允许依赖该结果的下一次模型请求。
- 工具已执行但结果保存失败时，记录或显式暴露 uncertain 状态，不能自动重放副作用。
- 每次关键 await 前后及最终提交处检查 epoch，拒绝旧运行的迟到写入。
- 项目、任务、分支、快照范围由宿主绑定，不能由模型自由传参越权；按 ID 直接读取也要做同样范围检查。
- 可选便条整理失败不应无条件停机；关键要求缺失、证据未保存、交接状态不一致则不得伪装成功继续变更操作。
- 检索索引失败可回退到范围内的直接读取；不允许回退成不带范围的全局搜索。
- 提示词与输入标签不是安全隔离。源数据库放在工作目录之外不等于模型无法读写；若需提供强隔离，必须使用实际权限/沙箱边界。首版未实现时明确写进威胁模型。
- 普通修改保留历史，但删除约束对旧快照同样生效。不要宣称已经发送到外部服务的数据能被本地撤回。

## 七、上下文策略

采用混合策略：有效近期上下文 + 最小任务接续包 + 旧工具结果移出并保留引用 + 按需检索 + 可选的带来源局部摘要。

不要固定每 N 轮清空，也不要每轮重写所有背景。不为追求“新记忆系统”而频繁换窗。

每个上下文代际使用稳定起始工作包，然后追加近期交互、检索结果和小型变更。任务阶段完成或达到预算安全边界时再重建。

必须保留当前有效的关键要求、未完成任务、阻塞性冲突；不能只靠相关性排序。工作包装不下必需内容时，应拆任务、限制工具范围或暂停，而不是偷偷丢要求。

预算覆盖完整请求：系统提示、工具定义、图片、消息、预留输出与工具结果空间。优先利用实际 Pi/提供方计数能力；无法精确计数就标明估计并使用可配置保守余量。

移出旧工具输出时保持提供方消息合法性：调用和结果配对、顺序、signed/opaque 数据与多模态规则。不能伪造 assistant 消息、补造思考或切开尚未完成的工具批次。

长结果先归档，再用有界展示和分页读取。无可检索原始证据时必须标注缺失。

逻辑任务可以长期存在，但 Pi 活动消息集合应有界。不能只在发送前过滤，却在内存里永久保留并深拷贝全部历史。

一个请求固定一个快照视图。缓存、索引和读取结果都带作用域与版本；不能混入不同分支或新旧修订。

## 八、安全交接与请求放行

把交接实现为明确状态机，而不是若干不受协调的回调：

RUNNING → QUIESCING → PERSISTING → BUILDING → VALIDATING → READY

失败进入明确的 FAILED/RECOVERY_REQUIRED 状态。只有经过验证的 READY 才允许新一代的模型请求和变更操作。

在已完成的工具批次边界停止，保存消息及结果，提交必要状态，组装并验证下一窗口，然后再切换。不要在处理中途破坏工具配对。

关键要求更新或用户取消必须按实际 Pi 队列语义正确处理；交接不得吞掉、重复消费或重排用户的新输入。

普通扩展错误可能不阻断执行，因此关键 gate 必须位于你验证过的宿主请求/工具边界。写测试证明 gate 失败时实际 provider 调用次数或工具调用次数为零，不只检查 UI 出现报错。

需要保留提供方后端线程时验证其隔离语义；严格新代际不得继续依赖携带后续历史的 thread/response 标识。不能假设换本地数组就清除了服务端状态。

非关键经验整理失败时，只要核心证据与有效工作区还安全，可继续旧窗口并告警；关键交接失败时保留旧状态或暂停，不能偷偷退回总摘要掩盖错误。

## 九、恢复策略

必须区分三项操作：

1. inspect：只读检查旧记录，不改变当前状态。
2. correct：在当前状态产生一次纠正提交，不整体倒退。
3. fork/resume：从检查点建立新分支与新 epoch，重新构建会话。

默认不执行破坏性 git reset、clean、checkout 覆盖用户工作。首版可只支持上下文续接及工作区匹配检查；未实现代码恢复，就不能标成完整工作现场恢复。

实际返工可显式导入选定失败经验，并标记来自旧尝试。严格历史模式不得自动导入后续信息；两种模式不能混用。

新运行重新绑定 SDK 事件、扩展及工作区资源。不在活进程脚下偷偷更换目录指针；旧句柄、后台任务、连接和输出必须被关闭或隔离。

工作区不匹配时先核实、进入受限恢复状态或请求明确选择，不直接把旧测试结果当当前有效。未知外部副作用不得自动重放。

## 十、最小界面

利用实际 Pi 支持的控件做一个小面板与命令入口。第一版只需要：

- 状态：模式、task、epoch、检查点、未归档/未整理范围和实际错误；不显示“记忆已绝对安全”。
- 任务约定与当前接续包：可以检查关键来源、提案和实际本轮加载内容。
- 检查点详情与差异、明确模式的续接确认。

UI-only 状态尽量不进入模型上下文。审批与恢复按钮调用宿主的受控操作，不是生成一句自然语言交给模型自己执行。

不要先开发 Web 前端、通用时间线编辑器或复杂知识图谱可视化。

## 十一、开发与验收

提供 off / record / active 模式，默认 off。off 保持原生行为；record 只记录且不改变模型输入；active 才接管续接。测试配置隔离，不修改全局默认。

先做一个端到端最小闭环：
用户给任务与关键限制 → 记录一次文件/工具行为 → 保存证据与工作记录 → 到安全边界 → 生成接续包 → 用新上下文继续 → 核对要求仍在、证据可查、未重放副作用。

优先 mock/fake provider 的离线测试，不依赖真实账号、计费 API 或外部服务。真实模型未测时明确写出；结构测试通过不等于记忆质量提升。

至少覆盖：
1. 早期要求未重复，后续只有“继续”，仍被保留。
2. 设想与确认决定分开，模型不能自授 confirmed/权限。
3. dirty 工作区导致旧验证结果失效或待核实。
4. blob/DB 故障不会发布不完整检查点。
5. 提交成功但响应丢失，按 op_id 恢复而不重复。
6. 旧 epoch 的迟到结果不能修改新运行。
7. 索引或缓存落后时不串分支，不绕过直接 ID 读取检查。
8. critical gate 失败时下一次 provider/变更工具不被调用。
9. 多工具与多模态消息重建仍符合已验证的提供方协议。
10. 交接中到来的用户修改、取消和 follow-up 不丢失、不重复。
11. strict history 与显式失败经验导入的区别可验证。
12. 可选便条或索引失败不会造成不必要的全局停机。
13. 模式 off 不改变基线行为。
14. 重启后恢复元数据有效，但不会重放 unknown 外部操作。

对 mock、SQLite 和真实适配边界分别测试；不能 mock 掉需要证明的 gate、事务或作用域过滤本身。

## 十二、实施顺序与交付

先完成：实际接口核查 → 独立核心 → fake provider 的两窗口闭环 → 真实 Pi 接入最小路径。之后再做完整恢复 UI 与对照评测。

第一轮务必进入代码与测试，不要只给我方案。小范围可自行做合理选择并记录，不为了普通技术选择反复提问。

只维护必要文档：README，以及 `docs/continuity/SPEC.md`、`UPSTREAM_AUDIT.md`、`VALIDATION.md`（已有等价文档可沿用）。规格写清范围与不变量，审计写实际版本和入口，验收写实际命令与结果。

最终汇报：
- 实际实现与改动路径；
- 关键设计取舍及 Pi 接入依据；
- 实际执行的测试命令、通过/失败/未执行；
- 最小启动与复现方式；
- 尚未实现、尚未验证的边界；
- 下一阶段应做什么。

不要声称“永不失忆”“彻底替代所有压缩”“跨系统原子恢复”“零成本”“质量已超过 Pi”或“生产可用”，除非有对应范围内的真实证据。不要为了全绿删除关键测试、放松隔离或关闭错误检查。
