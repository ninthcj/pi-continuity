# Continuity specification

The SQLite database is the authority. Blobs are written and flushed before their database reference is published. Every task is scoped by `project_id`, `branch`, and a monotonic `epoch`; semantic changes require the current contract `revision`. Late epoch writes raise an error. Evidence distinguishes source (`user_input`, `model_proposal`, `user_confirmation`, `tool_call`, `tool_result`, `model_request`, `model_response`, `resume`) and availability.

The active contract is a stable task id, revision, goal, acceptance list, and constraints list. A model proposal is evidence only. A confirmed change requires a host/user `sourceEvent`; model output cannot grant permission. A later explicit contract change increments revision and makes older request manifests stale by construction.

Memory claims are normalized by scoped subject, predicate, and value. Equal fingerprints are deduplicated while retaining the first claim's evidence. Divergent values for the same scoped subject/predicate create an informational conflict containing both immutable claims; it does not block recall, manifests, or provider calls. Conflicts have no resolution workflow or lifecycle status. An agent may produce a three-way merge proposal from a common base; a merge commit has both parent snapshots, preserves the original histories, and selects the newest conflicting claim by default. Older claims remain readable through their snapshots.

Recall is project/task scoped and returns a bounded preview with a stable memory ID; full content is read explicitly by ID. Recalled memory is guidance and evidence, not an authority source by itself. Current user input, confirmed contract state, and current workspace evidence remain authoritative.

The request view contains the current contract, current epoch, a bounded recent event set, budget and manifest id. A gate failure occurs before the provider call. `off` preserves the provider call path; `record` records request/response evidence while passing the caller's messages through; `active` uses the manifest gate.

Side-effect tools first create an operation intent. The result is recorded before later work can depend on it. Reusing a completed `op_id` returns its recorded result, and unknown operations are never automatically replayed; a host/user reconciliation is required before reuse. Epoch changes reject late results.

Checkpoint publication is two-phase (`BUILDING` then `READY`; errors become `FAILED`). `handoff` drives the host state machine `RUNNING → QUIESCING → PERSISTING → BUILDING → VALIDATING → READY`; failures are observable. `inspect` is read-only. `forkResume` requires a ready checkpoint and the current expected revision, increments the epoch, and records strict/practical mode. The implementation carries checkpoint context; it does not restore code or reset a worktree.

The current implementation is a single writer. Scope checks apply to direct id reads. The Pi host wraps `ModelRuntime.streamSimple` and can use `AgentSessionRuntime` replacement APIs so each new session gets a fresh gated runtime and subscription. Memory snapshots form a Git-like immutable claim-set DAG with deterministic tree hashes, but do not snapshot file bytes. Memory claims and snapshots may be recorded with historical epoch/revision metadata and remain readable across later task epochs. `exportMemory`/`importMemory` provide a versioned JSON exchange format for adapters to Mem0, Letta, Zep/Graphiti, Cognee, or LangGraph. `compressMemorySnapshot` creates a deterministic grouped view without deleting or rewriting claims. Search indexes, remote provider threads, hidden reasoning, credentials, and strong OS-level isolation are outside this package.

Workspace evidence is intentionally scoped: `captureWorkspace` hashes only explicitly listed files and records Git HEAD/dirty state when available. Resume can require a matching fingerprint and refuses to advance the epoch on mismatch. `backup` uses SQLite `VACUUM INTO` and copies referenced blobs, so the metadata file is not treated as a complete backup by itself.

Filesystem snapshots do not depend on Git. `createWorkspaceSnapshot` stores selected file bytes in the content-addressed blob store and records an immutable SQLite tree; `readWorkspaceSnapshotFile` can read historical bytes after the live workspace changes. Native APFS snapshots, one Windows VSS backend for both NTFS and ReFS, and Linux reflinks are optional accelerators. The portable copy-on-write equivalent is the correctness baseline across ext4, APFS, and NTFS.

Native capability reporting includes `requiresElevation` and a human-readable `permission`. Windows VSS for either NTFS or ReFS may require Administrator/`SE_BACKUP_NAME`, protected APFS volumes may require root or Full Disk Access, and Linux Btrfs/LVM snapshot operations may require root or `CAP_SYS_ADMIN`. Automatic mode is best effort and falls back to the portable backend; callers should display the capability result before requesting elevation. Native failure never makes the portable snapshot unavailable.

The selected backend mode is an application setting stored in SQLite by `setNativeSnapshotMode`; it persists across restarts until changed. This setting does not install drivers/services or grant operating-system privileges. `auto` remains non-blocking and falls back to portable-CAS when elevation is unavailable.
